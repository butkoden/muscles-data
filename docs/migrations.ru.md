# Миграции ресурсов

## Контракт Muscles Data

`muscles-data` предоставляет независимые от хранилища `MigrationRegistry`,
`MigrationSource` и обнаружение модулей миграций. Composition root приложения
создаёт один реестр, регистрирует в нём источники и передаёт реестр интеграции
с CLI. Реестр упорядочивает источники через `depends_on`, но сам не создаёт
подключения к БД. Подключения, журналы и выполнение принадлежат backend-пакетам.

Импорт классов и модулей миграций исполняет их код верхнего уровня: не открывай
соединения, не меняй данные и не запускай миграции при импорте. Сбор источников
не запускает `upgrade` или `downgrade`. `DataRuntime.migrations` содержит
реестр миграций. Консольные команды используют тот же объект `App.resource`, что
и HTTP-приложение; отдельный runtime для CLI не создаётся.

Файлы новых миграций можно хранить в Python-пакете владельца с именами
`m0001_*.py`, `m0002_*.py`. `discover_migration_modules(package_name)`
загружает исходный код таких модулей по имени и связывает его с контрольной
суммой, не обходя посторонние пакеты. Модули, уже импортированные другим путём,
или изменённые после обнаружения отклоняются; перезапусти процесс после правки.
Нумеруй версии с ведущими нулями: порядок проверяется лексикографически. Например,
`muscles-data-sql/examples/native_migrations.py` показывает обнаружение, план,
применение и откат на изолированной SQLite.

## CLI приложения

`muscles-data` предоставляет операции реестра, но не задаёт универсальный CLI.
Приложение может реализовать команды `status`, `plan`, `upgrade` и `downgrade`
поверх настроенного реестра. Обновление источника включает его зависимости.
Для отката нужно явно указать источник и целевую ревизию; применённые миграции
зависимого источника блокируют откат. `status` и `plan` не запускают миграции и
не создают журналы, но подключаются к существующей базе. Перед изменением схемы
проверь план, совместимость и резервную копию. Не запускай миграции при каждом
старте приложения.

## Блокировка и границы

Нативный SQL backend сериализует запись для одной БД: SQLite использует
`BEGIN IMMEDIATE`, PostgreSQL — транзакционную advisory-блокировку. SQLite
и PostgreSQL здесь поддерживаются только для SQL, допускающего транзакционный
откат в соответствующей СУБД. Миграция, самостоятельно завершающая транзакцию,
нарушает этот контракт.

`MigrationRegistry(execution_lock=...)` принимает фабрику общей блокировки и
держит её при применении и откате. Откат источника с зависимыми источниками без
общей блокировки запрещён. Все конкурирующие runner должны использовать один и
тот же координатор и обращаться к реестру, а не вызывать backend напрямую.
Для общих SQL-источников с одинаковым URL общая конфигурация выбирает
`SqlMigrationExecutionLock` автоматически. PostgreSQL
использует session advisory lock, SQLite — файл блокировки рядом с БД; для
SQLite все runner должны видеть один и тот же файл через общую файловую систему
с корректной поддержкой `flock`. Для разных или смешанных хранилищ приложение
должно передать в реестр собственный общий межпроцессный координатор. Без него
межресурсные `upgrade` не являются одной атомарной операцией, а откат источника
с зависимыми источниками запрещён. Статус — снимок, он может устареть.

## Журналы и совместимость

`NativeSqlMigrationBackend` хранит `source`, `revision`, `checksum` и время
применения в `muscles_data_migrations`. Все SQL-миграции одной операции и их
журнал изменяются в одной транзакции. `NativeSqlMigration.from_module` вычисляет
SHA-256 исходного `.py` файла; модуль обязан определить `revision`, `dialects`
(`"sqlite"`, `"postgres"`) и `upgrade(tx)`, может определить `downgrade(tx)`.
При изменённом или отсутствующем файле, расхождении контрольной суммы, неизвестной
или пропущенной версии выполнение останавливается. Без `downgrade` откат через
эту версию запрещён.

Каждый SQL-источник приложения регистрируется через
`NativeSqlMigrationSourceBackend` из `muscles-data-sql`; он управляет коротким
подключением и делегирует транзакционное выполнение `NativeSqlMigrationBackend`.
Все SQL-источники используют общий журнал `muscles_data_migrations`. Для базы, ранее
обслуживавшейся другим механизмом миграций, сначала нужно явно сверить схему и
начальное состояние журнала; не применяй начальные `CREATE TABLE` повторно.

Для собственных MongoDB/Redis-модулей `Migration.from_module(module,
resource=client_or_collection)` явно передаёт ресурс в `upgrade(resource)` и
`downgrade(resource)`; глобальное соединение не требуется. При самостоятельном
импорте модуля backend не может доказать, что уже загруженный Python-код
соответствовал файлу в момент импорта. Используй механизм обнаружения и
неизменяемые релизные файлы.

Redis/MongoDB backends находятся в пакетах соответствующих адаптеров;
`muscles-migrations` остаётся переходным слоем импортов и требует соответствующий
extra `redis` или `mongodb`. Для них операции данных и журнал не образуют общей
транзакции: прерванное применение или откат оставляют `running`/`reverting` и
блокируют повтор до ручного расследования. Их блокировки намеренно не истекают;
после аварии оператор сначала проверяет, что runner завершился, и состояние
данных, прежде чем вручную снимать блокировку. Redis использует выделенный
prefix и просматривает журнал по нему. Старые Redis-записи без имени источника
и версии можно сопоставить с известными файлами, но не с неизвестной миграцией:
если обнаружена неоднозначная старая запись, выполнение остановится до ручной
сверки; автоматически переписывать старую историю нельзя.

## Проверка

Проверяй статус до изменений, применение, повторное применение, откат, изменение
и отсутствие файла, прерывание, зависимости и конкурентный запуск на изолированной
БД каждого поддерживаемого backend. Объединённое состояние между разными
хранилищами не является распределённой транзакцией; при неудаче после успешного
источника реестр останавливается и оператор оценивает уже применённые изменения.
