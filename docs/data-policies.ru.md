# Политики данных и события жизненного цикла

Это руководство описывает контракты `muscles-data`, которые позволяют ограничивать доступ к объектам и подключать дополнительное поведение без зависимости пакетов друг от друга. Библиотека не знает о пользователях, рабочих пространствах или устройстве вашей базы: эти понятия задаёт приложение.

## Как компоненты работают вместе

1. Приложение аутентифицирует пользователя и проверяет его право работать с выбранной областью данных.
2. Для каждого запроса создаётся `DataOperationContext`: идентификатор субъекта и проверенные атрибуты области.
3. Пакет объявляет стабильный тип своего объекта в общем `DataRuntime`.
4. Независимый модуль регистрирует политику и, при необходимости, обработчик создания и удаления объектов.
5. Репозиторий, поддерживающий политики и события, применяет их при выполнении операции.

**Важно:** ни наличие контекста, ни регистрация политики сами по себе не защищают прямые запросы к базе. Защита работает только в адаптере, который её применяет. Пустой `DataPolicyPipeline` доступ не ограничивает. Авторизацию, проверку членства в области и создание доверенного контекста обеспечивает приложение.

## Контекст запроса и тип объекта

```python
from muscles.data.policies import DataOperationContext

# subject_uid и scope_id получены из проверенной сессии,
# а доступ пользователя к scope_id уже проверен приложением.
context = DataOperationContext(
    subject_type="user",
    subject_uid="user-1",
    attributes={"scope_id": "scope-1"},
)

# На этапе установки пакета; runtime — общий DataRuntime приложения.
runtime.register_object_type("documents", "demo:document", owner_field="owner_uid")
```

`attributes` — неизменяемое отображение; новый контекст создаётся для каждого запроса. Не сохраняйте текущую область в глобальном состоянии `DataRuntime` и не доверяйте идентификатору области только потому, что он пришёл из HTTP. `target` — имя ресурса или таблицы адаптера, `object_type` — стабильный идентификатор доменного типа. `owner_field` — метаданные для композиции и миграций; само по себе поле не добавляет проверку владельца.

Получить декларации можно через `runtime.object_type_for_target("documents")` и `runtime.registered_object_types()`. При конфликтующей повторной регистрации возникнет `ValueError`.

## Политика через отдельную таблицу связей

Политика получает `DataOperationRequest` с `kind`, `target`, `context`, `filters`, `values` и необязательным `object_type`. Возвращайте `DataPolicyDecision`: разрешение и обязательные предикаты, либо явный отказ. Несколько зарегистрированных политик объединяют ограничения через **И**; любой отказ вызывает `DataPolicyDeniedError`.

```python
from muscles.data.policies import (
    DataOperationKind, DataPolicyDecision, DataPredicate,
    DataPredicateOperator, DataRelatedExists,
)

class ScopePolicy:
    def evaluate(self, operation):
        if operation.object_type != "demo:document":
            return DataPolicyDecision()  # Этот модуль не управляет другими типами.
        scope = operation.context.attributes.get("scope_id")
        if not operation.context.subject_uid or not scope:
            return DataPolicyDecision(allowed=False, reason="Не выбрана доступная область")
        if operation.kind is DataOperationKind.UPSERT:
            return DataPolicyDecision(allowed=False, reason="Используйте create или update")
        if operation.kind is DataOperationKind.CREATE:
            return DataPolicyDecision()  # Связь появится после вставки объекта.
        return DataPolicyDecision(predicates=(DataPredicate(
            "uid", DataPredicateOperator.RELATED_EXISTS,
            DataRelatedExists("scope_links", "object_uid", {
                "scope_id": scope, "object_type": "demo:document",
            }),
        ),))

runtime.policies.register(ScopePolicy())
```

`RELATED_EXISTS` означает: значение поля `uid` объекта должно совпасть с `object_uid` в `scope_links`, а остальные поля связи — с заданными фильтрами. Одному объекту могут соответствовать несколько строк в разных областях. Реальная таблица, её индексы и проверка права субъекта на область принадлежат приложению.

Для `CREATE` проверка существования будущей связи не подходит: её ещё нет. При необходимости проверяйте разрешённые скалярные значения создаваемого объекта, а связь добавляйте событием в той же транзакции. Пример явно запрещает `UPSERT`: используемый SQL-адаптер проверяет предикаты upsert и на ветке создания, где `RELATED_EXISTS` не поддерживается. Если пакет не установлен, отсутствие его политики **не** означает автоматическое ограничение владельцем: приложение должно зарегистрировать подходящую политику владельца или иной обязательный механизм.

`DataPolicyDecision.replaces_owner_scope` — явное указание адаптеру, который отдельно реализует ограничение владельца, что политика уполномочена его заменить. Сам флаг ничего не фильтрует, и pipeline требует, чтобы вместе с ним был хотя бы один предикат. В `NativePolicyRepository` автоматического ограничения владельцем нет.

### Диагностика и неатомарная запись

`runtime.policies.explain(operation)` оценивает политику и возвращает тип операции, цель и названия полей с операторами без значений предикатов. Явный отказ по-прежнему вызывает `DataPolicyDeniedError`; диагностический вызов не выполняет операцию и не заменяет контроль в адаптере.

Для адаптеров, которые используют `DataPolicyPipeline.require_atomic_write`, режим по умолчанию запрещает защищённую запись, если условие нельзя проверить атомарно. `DataNonAtomicPolicyMode.ALLOW_PRECHECK` — явное ослабление: между предварительной проверкой и записью данные могут измениться. Включайте его только когда приложение принимает этот риск; наличие флага не делает произвольный адаптер атомарным и не заменяет транзакцию.

## Транзакционные события объекта

`runtime.object_lifecycle` — синхронный диспетчер `ObjectLifecycleEvent`: действие `created` или `deleted`, тип и идентификатор объекта, контекст операции. Он вызывается адаптером **внутри транзакции записи**. Тот же объект может обрабатываться несколькими независимыми модулями.

```python
def on_object_change(transaction, event):
    if event.object_type != "demo:document":
        return
    if event.action == "created":
        # INSERT связи с event.object_uid и event.context.attributes["scope_id"]
        # через тот же transaction; синтаксис зависит от SQL-драйвера.
        ...
    elif event.action == "deleted":
        # DELETE всех связей для (event.object_type, event.object_uid).
        ...

runtime.object_lifecycle.register(on_object_change)
```

При исключении обработчика транзакция отменяется: ни объект, ни связанные изменения не должны сохраниться. Не открывайте отдельную транзакцию для записи связи. Обработчики должны фильтровать типы и использовать параметры запроса. Если объекта не найдено при удалении, событие не создаётся. Обновление и чтение не порождают события жизненного цикла; для `upsert` событие создания возникает только при вставке. Эти гарантии относятся к адаптеру, который действительно вызывает `emit_object_event`.

Это не `EventPublisherPort` и не очередь сообщений: транзакционное событие не доставляется асинхронно, не сохраняется как журнал и не предназначено для сетевых вызовов в обработчике. Для внешней доставки нужна отдельная надёжная схема, например outbox, реализованная приложением.

## Проверка и границы

- Используйте контекст проверенного запроса для всех операций и создавайте таблицы с ограничениями и индексами, подходящими вашему приложению.
- Проверяйте доступ к **обоим** объектам при добавлении связи, а не только к основному объекту.
- Убедитесь, что список, пагинация, агрегаты, связанные записи и запись применяют политики до выдачи или изменения данных.
- Протестируйте отсутствие доступа из другой области и откат после ошибки обработчика.
- При отключении модуля, регистрирующего политику, предусмотрите отдельную политику владельца: пустой pipeline открыт.
- Исторические данные и их связи сами не переносятся. Перенос и порядок включения модулей организует приложение.

Практический SQL-пример и команды запуска см. в руководстве `muscles-data-sql` `docs/data-policies.ru.md`. Поддержка других хранилищ зависит от возможностей соответствующего адаптера.
